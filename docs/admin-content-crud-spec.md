# Удаление вложенных элементов

Удаление вложенного элемента в форме не должно сразу обращаться к базе.

Поведение:

1. Пользователь удаляет элемент.
2. Элемент исчезает только из локального состояния формы.
3. Реальное удаление выполняется после общей кнопки `Сохранить`.
4. Update action синхронизирует переданный массив с базой внутри одной Prisma-транзакции.

При отмене формы база не изменяется.

# Синхронизация вложенных данных

Для сложных обновлений используй Prisma `$transaction`.

Алгоритм для каждой вложенной коллекции:

1. Получить существующие записи.
2. Собрать `id`, присутствующие в DTO.
3. Удалить существующие записи, отсутствующие в DTO.
4. Элементы с существующим `id` обновить.
5. Элементы без `id` создать.
6. Синхронизировать translations.
7. Пересчитать `position` по текущему порядку массива.
8. Выполнить всё в одной транзакции.

Не используй полное `deleteMany` и повторное создание для всех элементов, если можно выполнить нормальную синхронизацию по `id`.

Для nullable one-to-one блоков фестиваля:

- `nominations`;
- `jury`;
- `organizations`;

поддержи три состояния:

- создать;
- обновить;
- удалить, если блок был удалён из формы.

# Server Actions

Для коллекционной сущности должны существовать операции:

```ts
getEntities();
getEntity(id);
createEntity(input);
updateEntity(id, input);
deleteEntity(id);
```

Названия можно адаптировать под конкретную сущность.

Каждый action должен:

1. содержать `"use server"`;
2. вызвать `requireAdminSession`;
3. валидировать input существующей Zod-схемой из `packages/types`;
4. не доверять данным клиента;
5. использовать Prisma Client из `packages/database`;
6. возвращать сериализуемый результат;
7. обрабатывать ожидаемые ошибки;
8. вызывать `revalidatePath`;
9. не вызывать `redirect()`.

Для read-операций допустимо использовать обычные server-side query-функции вместо Server Actions, если это лучше соответствует существующей архитектуре проекта. Мутации обязательно реализовать как Server Actions.

Локальный инфраструктурный тип результата допустим:

```ts
type ActionResult<T = undefined> =
  | {
      success: true;
      data: T;
    }
  | {
      success: false;
      message: string;
      fieldErrors?: Record<string, string[]>;
    };
```

Это не считается дублированием доменных типов.

При ошибке Zod возвращай `fieldErrors`.

Обработай как минимум:

- нарушение unique constraint;
- запись не найдена;
- неизвестную серверную ошибку.

Не показывай пользователю raw Prisma error.

# Критерии готовности

Работа считается выполненной, когда:

- все перечисленные маршруты существуют;
- все карточки dashboard ведут на правильные страницы;
- для всех коллекционных сущностей работает create/read/update/delete;
- singleton-сущности нельзя продублировать через UI;
- повреждённое singleton-состояние выводит ошибку;
- `EventsContent` редактирует один год с массивом событий;
- оба языка обязательны;
- вложенные элементы сохраняются одной транзакцией;
- удаление вложенного элемента происходит только после сохранения формы;
- загрузка изображений использует существующий MinIO-код;
- изображения имеют preview;
- действует ограничение 4 МБ;
- videos редактируются как URL;
- `achievements` редактируются как изображения;
- порядок меняется кнопками вверх/вниз;
- после create/update пользователь возвращается к списку;
- delete требует подтверждения;
- каждый mutating action проверяет admin session;
- после CRUD вызывается `revalidatePath`;
- Prisma schema не изменена;
- в `apps/admin` не появились копии типов и Zod-схем;
- lint и typecheck проходят без ошибок.

```

Отдельно стоит потребовать от Codex перед написанием файлов вывести короткий план и найденные фактические пути импортов. Это позволит сразу заметить неверно определённые exports из `packages/types`, `packages/database` или общего UI-пакета до массовой генерации CRUD-кода.
```
